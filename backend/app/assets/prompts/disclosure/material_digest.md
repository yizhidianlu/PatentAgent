# 材料消化（Step 2 · 逐文件 STRUCT 调用）

## 任务

平台已把用户上传的一份材料（Word/PPT/PDF 已由服务端转换为 Markdown，代码与文本原样）注入本调用；超长材料会被分片，多个分片的摘要卡由服务端归并。你的任务：按下表优先级判断该材料的价值，提取**可专利化**内容，产出一张结构化摘要卡（仅输出一个 JSON 围栏块）。

## 优先级表

| 优先级 | 文档类型 | 关注内容 |
|--------|----------|----------|
| 1 | 专利相关文档 | 专利点分析、已有交底书、专利申报建议、创新点汇总 |
| 2 | 详细设计/方案文档 | 详细设计、方案讨论、流程图、完整流程、技术对比分析 |
| 3 | 核心实现代码 | 算法与策略实现、业务逻辑与流程编排、数据处理与转换、规则引擎与决策逻辑、接口与集成设计、状态机与调度机制、性能优化与缓存策略、安全与权限控制等（依项目领域灵活识别） |
| 4 | 系统设计文档 | 系统设计、架构说明、模块划分、数据流与控制流 |

## 提取要点

- 记录**引用路径或文件名**，便于在交底书中写「参见某设计」时脱敏表述。
- 表格、编号列表、PPT 每页标题与正文、备注，均属可专利化叙述来源。
- 材料内嵌图片以其在 Markdown 中的引用与图题为准记入 `figures_mentioned`，不必逐图描述。

## 按专利类型加扫（实用 / 外观）

当前类型为**实用新型**或**外观设计**时，在通用优先级之外**额外**关注：

| 类型 | 加扫重点 |
|------|----------|
| 实用新型 | 装配图、爆炸图、结构说明、`structure_*.yaml/json`、零件表 |
| 外观设计 | 按要点落面收正投影/立体图（非默认六视）、效果图、色彩说明、`appearance_*.yaml/json` |


（识图填表与 figure_plan 由后续专门阶段完成，本调用只登记线索。）

## 输出契约（仅输出一个 JSON 围栏块）

```json
{
  "file": "原文件名",
  "priority": 1,
  "summary_zh": "3-6 句中文摘要：该材料讲什么、与可专利点的关系",
  "tech_points": ["材料中体现的候选技术点/创新点（短句）"],
  "components": ["出现的模块/部件/角色名（保留材料原词）"],
  "figures_mentioned": ["材料中提及或内嵌的图（图题/说明/文件名）"],
  "sensitive_hits": ["公司名、客户名、产品型号、内部代号、真实业务规模数字（日活/客户数/营收）等；**技术性能指标不算敏感项**"],
  "type_signals": {
    "invention": 0.0,
    "utility_model": 0.0,
    "design": 0.0,
    "evidence": ["支持类型判断的线索短句"]
  }
}
```

规则：

- `priority` 取 1–4，对应优先级表；不属于任何类别时取 4 并在 `summary_zh` 说明。
- `type_signals` 三个数值为 0–1 的类型倾向强度（方法/算法/流程 → invention；形状/构造/装配 → utility_model；造型/图案/色彩 → design），依据写入 `evidence`；服务端聚合后用于类型改判反问。
- `sensitive_hits` 供平台构建案件级敏感词表（脱敏口径见 common/desensitization.md）。
  **不要把本方案的技术性能指标列为敏感项**——准确率/灵敏度/特异度/时延/功耗/续航/
  吞吐/压缩比/模型体积等实测值是交底书「技术效果」章节的必要支撑，标进敏感词表会
  导致成文时被抹成定性描述，等于毁掉最核心的对比论证。也不要把标题领域对象当敏感词。
  真正要标的是：客户名、产品型号、内部代号、真实业务规模（日活/客户数/营收）、
  自建数据集的来源与采集对象身份。
- 分片输入时只描述本分片内容，归并由服务端完成。
